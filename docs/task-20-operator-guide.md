## Contract and inventory

The pinned all-time scope is **every stored session**, not a claim that Matter history is complete. Subsequent runs capture the selected parent estimates/daily reading fields (including generation-only dates), so preview old/new/delta compares the actual active baseline rather than stale raw derived columns. Each run pins timezone, `session-duration-225-round-v1`, `local-occurrence-day-v1`, source identity/revision, parent generation, owner/fence/expiry, progress and reconciliation. Choose the deployed `APP_TIMEZONE`, default `Europe/Athens`, explicitly. SQL evaluates binary64 division by 60, then multiplication by 225, and ties upward; it does not reorder the expression, use numeric division, nearest-even rounding, or add 0.5 before flooring. Checks include 2→8, 6→23, 130→487, 246→922, 262→982 and every integer 0–600. Entire duration belongs to the local occurrence date; calendar queries stay half-open. UTC source timestamps, duration, link/device metadata, and inferred intervals/article attribution are unchanged.

## Consistency and bounds

A snapshot identifier from Task 19 is not resumable. This engine uses a durable **writer barrier** instead. `repair_prepare` locks a singleton briefly and records `frozen=run`. Every session/daily mutation then fails SQLSTATE 55000 before row changes. Even an interrupted capture retains the barrier. Batches enumerate raw session IDs and daily dates while all those rows are frozen, making their stored immutable copies one coherent source. Metadata that cannot change sessions/daily remains available; deleting an item that cascades sessions meets the guard. No unrelated snapshots are combined. Every capture batch checks its original source revision and barrier; every verification batch checks its separately pinned verification revision. A lost/restored barrier with intervening source edits requires cancellation and a new capture, not reuse of previous chunks. Capture completion and thaw happen atomically; invalid capture thaws into `blocked`, never activates partial data.

This intentionally pauses session/daily ingestion during capture and verification, potentially across several invocations. It is a persistent flag, **not an open transaction or lock**. Deterministic ownership/expected-generation conflicts use SQLSTATE 55000, not serialization failure 40001 (Data API transaction adapters may retry that class). A failed page retains its cursor/receipt/dirty revision and can retry after thaw. Future production planning must budget that interruption and drain old deployments. Do not leave a frozen run unattended; resume or explicitly cancel it with the current fence. A crashed worker cannot cancel a successor.

Each `repair_batch` accepts 1–500 rows and 1–1,000 ms of loop work. Derived replacements and progress commit together. Inserts, updates behind the cursor and date moves after thaw are coalesced by session ID in a durable queue. Replacing a contribution subtracts its previous canonical contribution then adds its current one, in the same transaction. No retry double-adds. Active and immediate previous generations update synchronously on every session mutation (at most two). Earlier history is retained but no longer eligible for rollback.

`reconcile` requires an empty catch-up queue under the same mutex, then freezes raw inputs again. Bounded raw enumeration independently verifies membership, durations, dates, words and provenance, builds separate reference days, and checks all candidate/raw/reference dates. A stored cardinality counter detects extra candidate IDs without a whole-history count at cutover. Attempts/check rows remain retained. Invalid required data or mismatches block readiness. A new session/daily revision after thaw invalidates readiness and returns the run to catch-up. Cutover checks revision, epoch, current active generation, empty queue and complete reconciliation while holding that mutex; a racing writer either invalidates readiness first or maintains the newly active generation afterward.

The CLI uses separate short transactions with 5 s statement, 1 s lock and 10 s idle limits. SQL loop budgets are checked between rows; they do not preempt an individual indexed statement. Direct Data API callers must retain PostgREST's bounded statement timeout; an over-budget statement rolls back the entire batch. No engine transaction spans HTTP, a prompt, or operator deliberation. Extremely dense days/history can make indexed date enumeration exceed statement limits; failure is visible and must be investigated, never masked as completion.

## Cutover and rollback

Cutover changes a version pointer and epoch, rather than updating whole historical tables. The first valid capture constructs a value-preserving baseline; installing that baseline at thaw exposes the same old estimates/daily values, including unknown provenance and missing daily dates. Only a fully reconciled canonical candidate is eligible for the subsequent version switch. Unchanged canonical runs become `noop`, with no pointer or epoch change.

Daily derived reads merge only **reading seconds/words/session count/provenance** from one explicit generation. Current raw daily metadata provides item counts, highlights, source and timestamps. Obsolete reading dates have zero reading contributions, while unrelated metadata survives; the repair never deletes raw daily rows. Partial/ready candidates cannot be read as active data. A captured request generation remains explicit across paging and switches; this guarantees one derived version, not an MVCC snapshot of concurrent raw/metadata edits. A requested newly imported ID missing from a retired generation fails visibly instead of mixing estimates.

Rollback is fenced, uses expected active/epoch, and accepts only the immediately previous, synchronously maintained target. It refuses an outstanding repair or a retired/unmaintained target. Historical session estimates not superseded by ingestion restore exactly. Daily values/provenance restore exactly while the baseline source is unchanged. For sessions rewritten/imported since capture, the rollback target stores fresh canonical values. **After any session mutation, all baseline reading dates become canonical**, using already maintained full raw-session aggregates and one generation flag. Unknown old calendar semantics cannot identify every obsolete UTC bucket; refreshing only the new local dates could duplicate or omit contributions. This conservative reconciliation preserves the originals in immutable capture without reactivating stale daily totals. Immutable originals remain available for audit/export. This is deliberately a reconciled rollback, not a promise to reintroduce stale values after source changes. Unrelated daily metadata is never rolled back. Repeated rollback at its own epoch is idempotent; a later switch prevents a stale operator from overwriting it. Old request generations and earlier source/history are retained; there is no automatic GC.

Unresolved invalid IDs, null/nonfinite timestamps, null/negative/invalid durations, invalid known provenance timezones, unsafe totals, missing required inputs, query errors or membership/aggregate mismatches cannot become ready. Existing database constraints also prevent several malformed forms. Unknown old semantics/nullable stored words are explicitly unavailable optional explanations, not source corrections. Known old rollup divergence is reported as a counterfactual residual to repair, not proof of historical cause. The engine's independent **new** reconciliation must have zero unexplained mismatches. Do not correct raw history automatically: cancel, preserve/export evidence, and seek separate authorization for a correction policy before preparing a new run.

## Isolated operator commands

Use a dedicated libpq service file with a synthetic database and a least-privilege server role. No application Supabase/Matter credentials or inherited PGHOST/PGOPTIONS are used. Production is rejected, even if production variables are present. IDs below are example UUIDs; obtain actual active/epoch/fence from status. All commands explicitly select their target; inspection initiates no work.

```sh
export HISTORICAL_REPAIR_ISOLATED_ACK=yes
export HISTORICAL_REPAIR_ISOLATED_PGSERVICE=synthetic_repair
export HISTORICAL_REPAIR_ISOLATED_PGSERVICEFILE=/absolute/path/synthetic-services.conf
node scripts/historical-repair.mjs status --target isolated
# Before preparation, Task 19 remains the read-only live preview:
node scripts/historical-preview.mjs --target isolated --start 2026-01-01 --end 2027-01-01 --timezone Europe/Athens --out work/live-preview

node scripts/historical-repair.mjs prepare --target isolated --run 00000000-0000-4000-8000-000000000020 --owner 00000000-0000-4000-8000-000000000021 --active legacy --epoch 0 --timezone Europe/Athens
node scripts/historical-repair.mjs status --target isolated --run 00000000-0000-4000-8000-000000000020
node scripts/historical-repair.mjs execute --target isolated --run 00000000-0000-4000-8000-000000000020 --owner 00000000-0000-4000-8000-000000000021 --fence 1 --rows 500 --milliseconds 500
# Repeated bounded invocations; stop when capture ends / catch-up reports processed=0.
node scripts/historical-repair.mjs resume --target isolated --run 00000000-0000-4000-8000-000000000020 --owner 00000000-0000-4000-8000-000000000021 --fence 1 --rows 500 --milliseconds 500
# After worker expiry, another process claims with the observed fence (it increments).
node scripts/historical-repair.mjs claim --target isolated --run 00000000-0000-4000-8000-000000000020 --owner 00000000-0000-4000-8000-000000000022 --fence 1
node scripts/historical-repair.mjs preview --target isolated --run 00000000-0000-4000-8000-000000000020 --start 2026-01-01 --end 2027-01-01 --timezone Europe/Athens --out work/captured-preview.json
node scripts/historical-repair.mjs reconcile --target isolated --run 00000000-0000-4000-8000-000000000020 --owner 00000000-0000-4000-8000-000000000022 --fence 2
# Resume bounded verification to ready; then inspect status/control and independently review results.
# Use ACTUAL UUID and epoch from status, replacing the following example values:
node scripts/historical-repair.mjs cutover --target isolated --run 00000000-0000-4000-8000-000000000020 --owner 00000000-0000-4000-8000-000000000022 --fence 2 --active 00000000-0000-4000-8000-000000000023 --epoch 0
node scripts/historical-repair.mjs rollback --target isolated --run 00000000-0000-4000-8000-000000000020 --owner 00000000-0000-4000-8000-000000000022 --fence 2 --active 00000000-0000-4000-8000-000000000020 --epoch 1
# For an abandoned/blocked building run only; this releases its barrier, retains partial history:
node scripts/historical-repair.mjs cancel --target isolated --run 00000000-0000-4000-8000-000000000020 --owner 00000000-0000-4000-8000-000000000022 --fence 2
```

Each command completes its transaction before returning. There is no unbounded automatic execute loop. State determines the next action: `capture_sessions` → `capture_days` → `catchup`; explicit `reconcile` → `verify_sessions` → `verify_days` → `ready`; explicit `cutover` → `live`/`noop`. Retry a failed transaction using the durable status, not a locally advanced cursor. `claim`/`status` let a fresh process recover ownership; status serializes fences/epochs as decimal text. If a ready candidate changes to catch-up, drain and reconcile again. Captured preview supports explicit calendar partitions of at most 3,660 days and includes unavailable baselines/reasons; it describes capture time, while readiness proves current input separately.

## Migration, compatibility and future production gates

New additive migration: `20261014140402_bounded_derived_generations.sql`, created by supported Supabase CLI `2.48.3 migration new bounded_derived_generations`. Apply **after every existing migration**, including unchanged `20261014084407_estimation_provenance.sql`. It adds seven server-only RLS tables, fourteen exact-signature invoker functions with empty search paths, and four raw-table triggers; no repair starts on installation. No views, cron, queue or service are added. Catalog inventories and browser Data API tests cover the new objects. Immutable source has SELECT/INSERT only; the singleton has SELECT/UPDATE only; no service-role TRUNCATE grants. Server-role direct administrative edits are a trusted boundary, not an operator API.

For a future separately authorized run: obtain backups/exports of the full database plus generation/source/provenance and ingestion state; test restoration to an **isolated** target with raw/metadata/progress fingerprints and application security checks. Record backup identity, tested restore evidence, application/database versions and abort owner. Review preview/invalid policy and expected pause duration. Drain/disable all old writers and readers, scheduled execution, old Vercel deployments/previews and ad-hoc SQL importers; apply migrations; deploy compatible application code; verify server controls/roles and ordinary synthetic ingestion; only then separately authorize preparation and cutover. Never bypass triggers, change session primary keys, mutate immutable capture, or TRUNCATE active data. Changing APP_TIMEZONE requires an explicitly pinned compatible recomputation. Fencing does not protect against a privileged administrator disabling these controls. Older readers of raw persisted estimate columns cannot observe cutover and must be excluded; ordinary old session/daily DML is still guarded by triggers, but that does not make old reader deployments compatible.

Before a production transition, separately approve the exact expected active/epoch, complete reconciliation and preserved backup/restore evidence. Production credentials/targets require a future separately reviewed tool/workflow; this task does not enable them. Task 21 owns status UI; Tasks 23–24 own staging/release. Existing Git integration may create automatic branch previews; repair stays inactive unless an operator invokes prepare, and no preview is a production promotion.
